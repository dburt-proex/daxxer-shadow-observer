# Persistent Decision Ledger v0.1

Local implementation prepared November 14, 2026. Deployment is pending owner approval.
Read this alongside `DECISION_LEDGER_VERIFICATION.md` for executed results.

## What this covers

The collector accepts authenticated events independently of the folder observer.
One adapter wraps the existing `Ledger.append('episode', ...)` workflow. It
records an explicit human/agent-supplied purpose and authority reference before
the local append, then records the returned append receipt. This proves the
recording operation, not the truth of the episode or its real-world outcome.

The adapter is opt-in; existing `shadow.cmd record` and automatic folder capture
remain unchanged and are outside decision coverage. No ChatGPT, Claude, GitHub,
calendar, desktop or other integration is included. No historical data is imported.
Synthetic acceptance events have `simulated: true`.

## Event contract

All fields are required; nullable fields explicitly preserve unknowns. JSON
objects reject duplicate keys, non-finite numbers, unknown fields and bodies
larger than 16 KiB. Identifiers are bounded to 128 ASCII letters/digits/`_.:-`.
An event's source must match its bearer credential. Decision identity is the
pair `(source, decision_id)`. `received_at` is generated by the server and is
returned in the immutable receipt; clients cannot set it.

| Field | Meaning / constraint |
|---|---|
| schema_version | `0.1` |
| event_id, decision_id | Stable event ID and grouping ID; retry unchanged bytes semantically |
| project_id, directive_id | Explicit scope; immutable within one decision |
| related_record_ids | Up to 32 opaque record references; not fetched |
| occurred_at | Client-stated timezone-aware event time; not authenticated time |
| actor | `{id, type}`; type human, agent or system; asserted identity |
| source | Credential-bound source ID |
| kind | intent, decision, action, outcome, correction |
| purpose, rationale | Concise stated purpose/reason, never private model reasoning |
| decision, expected_result | Selected choice and prior expectation |
| authority_ref | Asserted instruction/approval reference; not an approval validator |
| action, execution_status | Attempt plus attempted/succeeded/failed/unknown/null |
| outcome | Evidence-supported stated result, or null |
| evidence_refs | Up to 32 opaque references; required for non-null outcome |
| unknowns | Up to 32 concise unknowns |
| classification | stated, observed, inferred, unknown |
| simulated | Required boolean; immutable within one decision |
| corrects_event_id | Required target for correction; null otherwise |

Text fields are nullable, nonblank when supplied, and at most 2000 characters.
References/unknown strings are bounded to 512 characters. Intent requires purpose
and expectation; decision requires choice, rationale and authority; action
requires action and status. A known outcome requires evidence references.

Storage adds monotonically increasing receipt sequence and server receive time.
Exact retry returns the original receipt; changed content with the same ID is
409. Distinct IDs cannot repeat the same primary stage within one decision.
Use correction annotations instead. Corrections preserve originals and make
the decision require review; they never silently change original intent.
Forward correction references are allowed and shown unresolved until present.

Arrival order does not determine lifecycle order. The read view checks stated
occurrence times. Missing stages, unknown outcome, inferred/unknown stages,
invalid chronology or corrections prevent a complete flag. Completeness means
record completeness, not verified correctness or authorized execution.

## API and authentication

| Method / path | Authorization | Result |
|---|---|---|
| GET /healthz | None | DB readability and process responsiveness; no records |
| POST /v1/events | Source token | 201 new, 200 exact retry, 409 conflict |
| POST /v1/heartbeat | Source token | Body exactly `{source: SOURCE_ID}`; server receive time |
| GET /v1/activity | Separate read token | Read-only JSON activity, incomplete decisions, stale sources, recent failures |

All activity requires a read credential. Writers cannot read activity; readers
cannot submit. Environment configuration stores SHA-256 token digests; raw,
random 256-bit bearer tokens stay with callers and the owner's secret manager.
Use distinct tokens per source and reader; revoke by replacing its digest and
restarting. Never commit tokens, environment files, records or outboxes.

Remote traffic must use HTTPS. The client rejects redirects and disables proxy
environment routing. HTTP is accepted only for numeric loopback development.
Body and connection limits constrain abuse but do not provide full DDoS
protection. The v0.1 service is for one small trusted deployment, not multitenant
public signups. Permission to send events does not grant authority to execute
the described action.

Submission failures record only server time, authenticated source and fixed
error category. Body, token and exception contents are suppressed. If DB audit
storage is unavailable, stderr logs the fixed failure category and HTTP returns
503. Preserve host logs; full-disk and prolonged load require operator action.

## Run and integrate locally

From the repository root, Python 3.11+:

```powershell
python -m pip install --require-hashes --only-binary=:all: -r requirements-collector.txt
# Configure LEDGER_SOURCE_DIGESTS, LEDGER_READER_DIGEST in your process securely.
# Source mapping example structure: {"shadow-reviewed-record":"<64-hex SHA256>"}
python -B scripts/decision_collector.py serve
```

Defaults: numeric loopback port 8080, `runtime/decision-ledger.sqlite3`, four
Waitress threads, 16 KiB body limit and stale threshold 180 seconds. Only the
deployment proposal binds 0.0.0.0 behind the provider's TLS ingress.

Generate random tokens locally with `secrets.token_urlsafe(32)` and hash their
UTF-8 bytes with SHA-256. Supply values through a secure terminal/secret store;
do not send them in chat or use placeholder digests. Each actor/source claim
remains an assertion by whoever possesses the source token.

Create a reviewed context JSON containing exactly `project_id`, `directive_id`,
`purpose`, `rationale`, `expected_result`, `authority_ref`, and `simulated`.
Review it to exclude secrets/full transcripts/unrelated personal activity.
The reviewed episode stays local; only its ID, payload hash and returned
record hash are referenced remotely.

```powershell
# LEDGER_URL and LEDGER_SOURCE_TOKEN supplied securely to this process.
python -B scripts/decision_adapter.py record --input work/reviewed-episode.json --context work/reviewed-context.json --record-id UNIQUE_RECORD --decision-id UNIQUE_DECISION --outbox runtime/outboxes/UNIQUE_DECISION.sqlite3
python -B scripts/decision_adapter.py status --outbox runtime/outboxes/UNIQUE_DECISION.sqlite3
python -B scripts/decision_adapter.py flush --outbox runtime/outboxes/UNIQUE_DECISION.sqlite3
python -B scripts/decision_adapter.py heartbeat
```

Use one new outbox per execution, one writer per outbox, decision ID <=110
characters, and a fully initialized existing local experience ledger. Intent
and decision must be acknowledged before action. If delivery fails, the outbox
retains pending events and attempts for explicit replay. Replay never repeats
the local append. Any existing outbox blocks execution; inspect the original
local record before starting a new decision. A crash between the local append
and outcome enqueue leaves a visible missing outcome: inspect the local ledger
and add a reviewed correction, never infer or automatically re-execute it.

Heartbeat is an explicit command, not an installed timer. The caller supervisor
must submit it every 60 seconds for live connection reporting. A stale source
is visible after 180 seconds when activity is read. No alerts or automatic
scheduling are installed. A healthy collector does not imply healthy sources.

## Durability, backup and restore

SQLite WAL, `synchronous=FULL`, short transactions and unique source/event keys
provide atomic acknowledged writes under normal filesystem durability guarantees.
Update/delete triggers protect API application paths, not a DB administrator.
There is no cryptographic authenticity or tamper-proof guarantee. Root access,
stolen tokens, whole-history rewrite, untrusted source statements and deleted
backups remain risks. Existing Observer hash chains are unchanged and provide
no independent external integrity anchor by themselves.

Create a transactionally consistent SQLite backup (can run while serving):

```powershell
python -B scripts/decision_collector.py backup --destination runtime/backups/ledger-UNIQUE.sqlite3
```

Keep the returned SHA-256 receipt separately. Do not simply copy the live main
DB and omit its WAL. Back up local adapter outboxes and Observer streams/evidence
separately while their writers are stopped. Backups contain sensitive plaintext:
encrypt and retain only in an owner-approved destination. No external backup
transfer or retention policy has been activated. Initial proposed recovery point:
daily backup, with operator-reviewed retention; approval needed to install it.

Restore drill: stop writes/collector; preserve the original DB, WAL/SHM and
outboxes; verify backup hash and `PRAGMA integrity_check`; copy backup into a new
empty directory; point LEDGER_DB at the restored copy; start, read activity and
verify counts/IDs; replay pending outboxes using original IDs. The automated
test exercises backup-to-new-path restore and duplicate replay. It does not
prove remote disk snapshots or disaster recovery on a hosted provider.
